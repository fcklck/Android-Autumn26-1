# Kotlin. Практикум

Вам предстоит поупражняться в возможностях языка Kotlin на примере работы
с результатами участия вымышленных футболистов в вымышленном чемпионате.

## Дано

Файл `src/main/resources/fakePlayersDirty.csv` — таблица о 250 вымышленных
футболистах, столбцы:

1. имя игрока
2. его команда и город, откуда она
3. позиция на поле
4. страна
5. агентство, представляющее интересы игрока
6. трансферная стоимость
7. кол-во участий в матчах
8. кол-во голов
9. кол-во голевых передач
10. кол-во желтых карточек
11. кол-во красных карточек (удалений)

Данные неидеальны: встречаются пустые ячейки, названия позиций в разном
регистре, лишние пробелы. Ваш парсер должен переживать это без падений
(см. правила маппинга ниже).

Рядом лежит «чистая» копия — `fakePlayers.csv`: она пригодится в тестах,
где нужны предсказуемые данные.

## Задание 1. Модель и маппинг

Реализуйте модель предметной области и маппинг «строка CSV → объект»:

- `Player`, `Team` — data-классы.
- `Position` — enum: константы, встречающиеся в файле, у каждой — русское
  название («нападающий», «полузащитник», «защитник», «вратарь») и
  companion-функция `fromCsvTokenOrNull(token: String): Position?`,
  не зависящая от регистра и лишних пробелов.
- Единственное nullable-поле игрока — агентство: `null` означает
  «интересы игрока никто не представляет» и является частью предметной
  области, а не ошибкой данных.

Правила маппинга, которым должен следовать парсер:

| Что встретилось в ячейке                | Что делать            |
|-----------------------------------------|-----------------------|
| Пустое агентство                        | `null`, игрок остаётся в выборке |
| Позиция в любом регистре, с пробелами   | нормализовать и распознать |
| Лишние пробелы в текстовых полях        | обрезать              |
| Пустая или нечисловая стоимость, голы, передачи, карточки, матчи | пропустить строку |
| Пустые имя, команда, город, страна, позиция | пропустить строку |

Парсер не должен падать на некорректных строках, а по итогам парсинга
должно быть известно, сколько строк пропущено (например, верните
`ParseResult(players, skippedCount)`).

## Задание 2. Запросы (обязательные)

Реализуйте интерфейс `IResolver`, он уже объявлен в проекте:

1. Количество игроков, интересы которых не представляет агентство.
2. Автор наибольшего числа голов среди защитников и их количество.
3. Русское название позиции самого дорогого немецкого игрока.
4. Команда с наибольшим средним числом красных карточек на одного игрока.
5. Средняя трансферная стоимость по позициям — позиции отсортированы
   по убыванию средней стоимости.
6. Топ-3 самых полезных игроков по формуле «голы + 2 × голевые передачи»
   (при равенстве — раньше по алфавиту имени).
7. Для каждой страны — самое популярное среди её игроков агентство
   (при равенстве — по алфавиту).
8. Посчитайте медианную трансферную стоимость и ответьте: какую долю всех
   голов забили игроки не дороже медианы, а какую — дороже.

## Задание 3. Запросы (дополнительные)

Любая из задач даёт дополнительные баллы, которые идут в зачёт активности
на парах. В скобках подсказано, что попробовать.

9. **Команда-агрегат.** Пусть `Team` хранит список своих игроков, а суммарная
   стоимость состава и среднее число карточек считаются лениво и
   переиспользуются в задаче 4. (делегирование `by lazy`)
10. **Потоковое чтение.** Найдите первого игрока стоимостью больше 50 000 000,
    проведшего не менее 25 матчей и ни разу не получавшего карточку, не
    загружая файл целиком в память. (`useLines`, `Sequence`, `firstOrNull`)
11. **Фильтры.** Опишите условия отбора игроков иерархией
    `sealed interface PlayerFilter` — `ByPosition`, `CheaperThan`, `And`,
    `Or`, `Not` — с функцией `matches(player: Player): Boolean` через
    исчерпывающий `when` без `else`; переформулируйте через фильтры пару
    запросов из задания 2. (sealed-иерархии, рекурсия, `when`)
12. **Мини-DSL отчёта.** DSL — это маленький встроенный язык для конкретной
    задачи: код читается не как последовательность шагов «создай список,
    добавь строку, отформатируй», а как описание самой сущности — отчёта,
    конфигурации, маршрута. Так устроены `build.gradle.kts`, маршруты Ktor и
    библиотека Kandy, которая понадобится вам в задании 4: на их месте мог бы
    быть громоздкий процедурный код, но вместо него — лаконичный и
    самодокументируемый. Здесь вы напишете такой язык для консольного отчёта,
    чтобы его вывод описывался декларативно:

    ```kotlin
    report {
        metric("Без агентства") { players.count { it.agency == null } }
        section("Атаки") {
            metric("Всего голов") { players.sumOf { it.goals } }
        }
    }
    ```

    Чтобы это заработало, понадобятся функции высшего порядка и лямбды
    с приёмником — главный «взрослый» приём Kotlin, на котором держатся
    все промышленные DSL.

## Задание 4. Вариант с визуализацией

Вариант выдаётся по номеру в списке. В каждом варианте две задачи — базовая
и продвинутая, выполните обе. Библиотеки на выбор:
[JFreeChart](https://www.jfree.org/jfreechart/),
[Kandy](https://kotlin.github.io/kandy) и другие.

**Вариант 1. Состав**
- Базовая: покажите, какую долю от всех игроков занимают игроки каждой
  из позиций.
- Продвинутая: покажите структуру составов топ-5 команд по суммарной
  трансферной стоимости — из графика должно быть видно, из каких позиций
  состоит каждая команда.

**Вариант 2. Цена и результативность**
- Базовая: покажите топ-10 команд по суммарной трансферной стоимости.
- Продвинутая: покажите, как связаны трансферная стоимость и число голов
  у нападающих, — выделите тренд скользящим средним (его удобно посчитать
  через `windowed`) и отразите жёлтые карточки, например цветом.

**Вариант 3. Распределения**
- Базовая: покажите, как распределены трансферные стоимости всех игроков.
- Продвинутая: покажите разброс трансферных стоимостей внутри каждой позиции
  так, чтобы позиции было удобно сравнивать между собой.

**Вариант 4. Страны**
- Базовая: покажите, какую долю занимают игроки из разных стран.
- Продвинутая: покажите топ-10 команд по суммарной трансферной стоимости
  и их накопленную долю — из графика должно быть видно, какая часть общей
  стоимости концентрируется в лидерах. (накопление удобно считать через
  `runningFold`/`scan`)

## Задание 5. Тесты (обязательные)

Покройте тестами правила маппинга (пустое агентство → `null`, пропуск «битых»
строк и подсчёт пропущенных, распознавание позиций в любом регистре) и каждый
запрос `IResolver` — удобнее всего на маленьком наборе из 2–3 экземпляров
`Player`, созданном прямо в тесте.

Используйте `kotlin.test`: зависимость и запуск через Gradle уже настроены,
пример теста лежит в `src/test/kotlin/InfrastructureTest.kt`.

## CI

При пуше в любую ветку и при создании PR запускается GitHub Actions:
сборка и тесты. PR с красным CI на ревью не берём.

## Как сдавать

1. Клонируем репозиторий себе
2. Переключаемся на ветку, названную по своему имени (например IvanovIA)
3. Выполняем задания
4. Делаем коммит, пушим ветку в удаленный репозиторий
5. В гитхабе создаем pull-request и подписываем **своей фамилией на кириллице**.
   К пуллреквесту прикладываем скриншоты: выполнение консольной части
   и получившиеся графики.
6. Ждем одобрения или комментариев на ревью, а баллов - в ведомости

## Запуск решения

Проект запускается обычной Gradle-командой:

```bash
./gradlew test
./gradlew run
```

`run` читает `fakePlayersDirty.csv`, печатает отчёт по обязательным и
дополнительным запросам и сохраняет графики варианта 4 в
`build/reports/football/`: `countries.png` и `top-teams.png`. При необходимости
путь к CSV и каталог вывода можно передать двумя аргументами:

```bash
./gradlew run --args="path/to/data.csv path/to/output"
```

В реализации использованы безопасный маппинг строк с подсчётом пропусков,
ленивые агрегаты `Team`, потоковый поиск через `useLines`, композиция
`PlayerFilter` и небольшой DSL консольного отчёта. Вариант 4 показывает доли
игроков по странам и топ-10 команд с накопленной долей общей стоимости.
